# 機体下基板におけるセンサーの取り扱いについて
超音波センサ、LiDARの取り扱い上の注意について述べる。なお気圧温度センサについては、ここでは省略する。あれはサンプルコードそのまま。

## 1. 超音波センサー URM37
超音波センサー URM37の読み取り方法はいくつかある。PWM, UART, アナログ電圧の3通りである。少なくとも24, 25, 26代ではPWMで読み取る方式を用いてきた。本項目ではPWMで読み取る方式を解説しつつ、PWM方式の問題点について言及する。

### 1.0 TL;DR
URM37をPWM方式で読むのはやめよう。読み取りに時間がかかって読み取り中はほかの処理が止まる（ブロッキング処理）。UARTがいいんじゃない？

### 1.1 各読み取り方式の概要

| 読み取り方式 | 特徴 |
| --- | --- |
| PWM | 26代まではこの方式。パルス幅を読み取って距離に変換する。ちなみにネットにあるサンプルコードの大半はこれ。 |
| UART | シリアル通信で距離の値そのものが送られてくる。ちなみにURM37には温度センサがついていてUARTだと温度を読める。 |
| アナログ電圧 | 電圧の高低から距離に変換する。精度はほかの方式に比べ劣る。 |

### 1.2 PWM方式での読み取り（一番ベーシックな方法）
URM37の出力端子から出てくるパルス幅を読み取り、それを距離に変換する。パルス幅が長いほど距離が長い。距離[cm] = パルス幅[µs] ÷ 50で求める(50µsが1cmに相当)。インターネット上のサンプルコードの大半は[このような処理](https://wiki.dfrobot.com/sen0001/docs/21980)で行っている。

しかし、このコードには問題点が存在する。パルス幅を読み取る方式であるため、`pulseIn()`関数を用いてURECHO端子に来るパルスが`LOW`になっている時間を計測している。この場合URECHOがHIGHからLOWになり、そしてHIGHになるまで（つまり超音波を発射して帰ってくるまで）の間、**ここで処理が止まってしまう。**

```c
void loop()
{
  Serial.print("Distance=");
  digitalWrite(URTRIG, LOW);
  digitalWrite(URTRIG, HIGH);              
  unsigned long LowLevelTime = pulseIn(URECHO, LOW) ; // ！！ここで処理が止まってしまう！！（ブロッキング処理）
  if (LowLevelTime >= 50000)              // the reading is invalid.
  {
    Serial.println("Invalid");
  }
  else
  {
    DistanceMeasured = LowLevelTime / 50;  // every 50us low level stands for 1cm
    Serial.print(DistanceMeasured);
    Serial.println("cm");
  }
  delay(200);
}
```
どれぐらいの間処理が止まってしまうのか概算する。待ち時間の内訳は、音波がセンサ→湖面→センサと往復するのに必要な時間+パルス幅の読み取りにかかる時間。URM37は最大測定可能距離が8mなので、音波が往復16mを進むのに必要な時間は往復16m ÷ 343m/s ≒ 約47ms。次に8mの場合、パルス幅は800cm × 50µs = 40msとなる。そのため最大で40ms+47ms=87msの間処理が止められることになる。

我々は100Hzつまり10msに1回の読み取りを目標にしていたため、ほかの処理に影響を及ぼすことになってしまう。

### 1.3 PWM方式で無理やり非ブロッキングな処理で読み取る
我々が今まで使ってきた処理がブロッキング処理であることに気づいたのはなんと**7月前半**のことであった。基板の修正が不可能な時期であったため、以下のような方式で非ブロッキング処理となるよう解決した。

処理の概要：

```text
trigger_echo()            → TRIGをLOWにしてHIGHに戻し、測定を開始(待機状態へ)
   ↓ (センサが測定中、loopは回り続ける)
echo_isr() 立ち下がり     → LOWの開始時刻を記録
echo_isr() 立ち上がり     → LOWの時間を計算し、ready フラグを立てる
   ↓
update_echo_distance()    → 毎周呼ばれ、readyなら距離に変換。一定時間来なければタイムアウト
```
詳しくは[該当コード](https://github.com/torica-org/2026-fm-archives/blob/main/Software/Underside/26th_Underside/URM37.cpp)を読んでください。


### 1.4 UARTを用いる場合
UART経由でURM37にコマンドを送る。[リファレンス](https://wiki.dfrobot.com/sen0001/docs/21975)にコマンドの説明がある。あとは[温度読み取りのコード](https://wiki.dfrobot.com/sen0001/docs/21977)を参考に距離を読むように書き換えれば読み取ることができるはず。

## 2. シングルポイントLiDAR TSD20

25代までは離陸判定に気圧高度などを用いてきたが、判定の精度に難があるため26代からはLiDARを新たに導入した。読み取り方法や取扱において特筆すべき事項を述べる。

### 2.0 TL;DR
- 買ってきてそのまま使えるのがUARTでの読み取り。ただそのまま受信するだけで読み取れない。
- UARTならばLiDAR専用のUARTピンを割り当てなければいけない。機体下のマイコンはXIAOだからピン少ないよね？マイコンのピン足りる？？SDだけで結構消費するよ？？
- I2Cで読み取ると気圧温度センサと共通のピンが使えて、ピンの数が足りなくて苦しむことがない。詳しくは取説を読もう

### 2.1 読み取り方法（一番ベーシックな方法）
UARTを使って読み取る方法である。26代で採用した。→[該当コード](https://github.com/torica-org/2026-fm-archives/blob/main/Software/Underside/26th_Underside/tsd20.cpp)

- 以下のように距離情報がそのまま送られてこないため、受信側でひと手間処理をする必要がある。[ユーザーマニュアル](https://akizukidenshi.com/goodsaffix/TSD20%20user%20manual.pdf)を熟読すること。
  
  ```text
  UARTで送られてくるデータの構造
  Byte    内容           例
  1     Frame Header    0x5C（固定）
  2     Distance_L      0x02
  3     Distance_H      0x11
  4      Checksum       0xEC

  距離データはlittle-endianのため下位バイト→上位バイトの順に送られてくる．
  0x02,0x11の順に来た場合，距離は0x1102 = 4354mmとなる．

  チェックサムの仕組み：0x02,0x11の場合
  0x02+0x11 = 0x13
  ビット反転(NOT)→ ~0x13=0xFF - 0x13 = 0xEC
  ```
- 工場出荷時はUARTモードが有効になった状態であるため、UARTで読むのが一番簡単。
- UART通信なので、エアデータとの通信以外にもう一系統UARTを用意する必要がある。XIAO RP2040はピンの数が少なく、LiDARで2ピンを消費するのは結構痛手。
- 使えるピンが全くなかったため、`XIAO RP2040 (TX) -> LiDAR TSD20 (RX)`の配線は省略した。なおプログラム上、RXのみの設定はできないためダミーのTXピンを割り当ててある。

### I2Cで読み取る
I2Cで読み取るとUARTと比べてマイコンのピンの節約になる。例えば気圧温度センサと共通のピンで読み取れるようになる。詳しくは[ユーザーマニュアル](https://akizukidenshi.com/goodsaffix/TSD20%20user%20manual.pdf)のp.5参照。
